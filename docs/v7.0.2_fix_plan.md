# V7.0.2 修复方案

## 一、根因回溯

三个问题汇聚到一个根因上——`LearningObserver._init_database()` 的 schema 兼容性问题。

```
                         LearningObserver 初始化失败
                                │
                    ┌───────────┼───────────┐
                    ▼           ▼           ▼
            evolution_learn  evolution_    evolution_
              不可用        run_cycle     self_monitor
                             不可用         不可用
                    │
                    ▼
            post_tool_call hook
              observer=None → 直接跳过
                    │
                    ▼
            HAE 原生工具性能
              never tracked
```

**完整根因链：**

### 1.1 Schema 不一致（主根因）

`observer.py` 的 `_init_database()` 逻辑：

```python
# 步骤1：创建表（有 outcome TEXT 列）
CREATE TABLE experiences (outcome TEXT NOT NULL, ...)

# 步骤2：创建索引（成功）
CREATE INDEX idx_outcome ON experiences(outcome)

# 步骤3：试图添加虚拟列（失败但被吞）
ALTER TABLE experiences ADD COLUMN _outcome TEXT
    GENERATED ALWAYS AS (json_extract(context, '$.outcome')) STORED
# ← ALTER 失败：outcome 是独立 TEXT 列，不是 JSON 字段的提取目标

# 步骤4：创建虚拟列索引（崩溃）
CREATE INDEX idx_exp_outcome ON experiences(_outcome)
# ← 崩溃：_outcome 列不存在 → sqlite3.OperationalError
# ← 整个 _init_database 抛异常，LearningObserver.__init__ 失败
```

### 1.2 设计谬误

代码假设 `outcome` 数据在 `context` JSON 字段里，但建表语句中 `outcome` 是独立的 TEXT 列。虚拟列 `_outcome` 试图从 `json_extract(context, '$.outcome')` 取值，这是错误的——`outcome` 不在 `context` 里。

### 1.3 错误处理不当

`ALTER TABLE` 失败被 `except sqlite3.OperationalError: pass` 吞掉，但后续 `CREATE INDEX` 没有用 `try/except` 保护，直接崩溃。

## 三、修复方案

### 3.1 修复 observer.py（删除虚拟列逻辑）

**文件**：`src/evolution/learning/observer.py`，`_init_database` 方法

**删除**：第 85-98 行（ALTER TABLE + CREATE INDEX 虚拟列部分）

**理由**：
- `outcome` 已是独立 TEXT 列且有 `idx_outcome` 索引
- 虚拟列 `_outcome` 是冗余设计，且实现有误
- 同理 `_experience_type` 也是同样的问题（`experience_type` 也是独立列）

**改动（删除 14 行）**：

```diff
-        # JSON 生成列索引（高频查询加速）
-        try:
-            cursor.execute(
-                "ALTER TABLE experiences ADD COLUMN _experience_type TEXT "
-                "GENERATED ALWAYS AS (json_extract(context, '$.experience_type')) STORED"
-            )
-        except sqlite3.OperationalError:
-            pass
-        try:
-            cursor.execute(
-                "ALTER TABLE experiences ADD COLUMN _outcome TEXT "
-                "GENERATED ALWAYS AS (json_extract(context, '$.outcome')) STORED"
-            )
-        except sqlite3.OperationalError:
-            pass
-        cursor.execute('CREATE INDEX IF NOT EXISTS idx_exp_type ON experiences(_experience_type)')
-        cursor.execute('CREATE INDEX IF NOT EXISTS idx_exp_outcome ON experiences(_outcome)')
```

### 3.2 验证其他依赖 LearningObserver 的模块

`observer.py` 修复后，以下自动恢复：

- `_get_learning_observer()` → 不再返回 None
- `evolution_learn` → 可正常写入
- `evolution_run_cycle` → orchestrator 可初始化
- `evolution_self_monitor` → SelfMonitor 可访问
- `post_tool_call` hook → observer 可用，自动追踪所有工具

### 3.3 evolution_recall_lessons 可见性

不需要代码修改。新会话启动后自动可见。

如用户要求新会话立即生效：`/new` 或重启 CLI。

## 四、举一反三

### 4.1 同类风险扫描

**SQLite schema 迁移代码审查**：搜索所有 `ALTER TABLE ADD COLUMN` 语句，检查是否有类似的冗余虚拟列设计。

```bash
grep -rn "ALTER TABLE\|ADD COLUMN\|GENERATED ALWAYS" src/ --include="*.py"
```

### 4.2 防御性修复建议

1. **错误处理加固**：`_init_database` 中每个 SQL 语句都应被 `try/except` 包裹，记录错误但不中断
2. **Schema 版本管理**：增加 `_schema_version` 表，迁移逻辑基于版本号而不是 try/except 试探
3. **数据库健康检查**：在 `hermes-evolution check` 中加一项——验证所有数据库的 schema 与代码预期一致

### 4.3 测试加固

新增测试用例：

    # 断言 observer 不为空，能正常记录经验
